## 1. Intent Brief（可直接给其他 skill 复用）

### 1.1 一句话目标（Outcome）

- 目标：把项目依赖更新到“最新稳定且可生产使用的主版本”，并确保升级后项目能构建、测试通过且关键路径不回归。
- 非目标：不做大规模重构/架构调整；不引入不必要的新依赖；不追求把所有传递依赖都强行升到最新。

### 1.2 交付物（Deliverables）

- 输出物：
    - `documents/deps-upgrade-report.md`（依赖现状 + 最新版本 + 变更/风险评估 + 升级顺序）
    - `Cargo.toml`/`Cargo.lock` 变更（以及必要的源代码适配）
    - 验证记录（执行的命令与结果）
- 受众：维护 `load-ants` 的 Rust 开发者/发布负责人。

### 1.3 约束与优先级（Constraints）

- 时间窗口：未明确（默认可进行多次迭代、小步提交）。
- 预算/资源：本地可运行命令与测试；网络可用（用于查询 crates.io 最新版本与变更记录）。
- 合规/安全：优先稳定版本；避免引入已知高风险/弃用依赖；关注 TLS/HTTP/DNS 相关依赖的安全修复。
- 性能/可靠性：不能显著降低吞吐/延迟；DNS 转发与 DoH 请求必须可用。
- 可逆性：必须能通过 `git diff` 复盘与回滚（小步升级，逐个依赖验证）。
- 优先级排序：正确性/可回滚 > 测试覆盖与验证 > 依赖“最新化”程度。

### 1.4 现状与证据（Current State）

- 现状描述：单 crate 项目（Rust 2021），`Cargo.toml` 已包含 `axum`/`tokio`/`reqwest`/`hickory-*`/`prometheus` 等网络与异步核心依赖。
- 证据/复现路径：仓库根目录存在 `Cargo.toml` 与 `Cargo.lock`（2026-03-07 更新）。
- 已尝试与失败：无（本轮由我执行盘点与升级）。

### 1.5 验收标准（Definition of Done）

- [ ] `cargo fmt -- --check` 通过（如项目启用格式检查）
- [ ] `cargo clippy -- -D warnings` 通过
- [ ] `cargo test` 通过
- [ ] `cargo run -- -c .\\config.default.yaml --test` 通过（至少覆盖配置加载/校验路径）
- [ ] 生成依赖升级报告（包含版本证据与风险说明）

### 1.6 风险与未知（Risks & Unknowns）

- 关键风险：
    - 主版本升级导致编译失败/行为变化（尤其：`hickory-*`、`reqwest*`、`axum`/`hyper`、`validator`）。
    - 依赖升级带来 MSRV 提升（虽然当前环境 `rustc 1.93.1`，但发布环境未知）。
    - TLS/openssl 相关依赖（`native-tls`、`openssl-sys`）在 Windows/Unix 的构建差异。
- 未知项：CI/发布流程、生产运行环境的 Rust 版本与系统依赖、是否需要锁定某些依赖以保持兼容。
- 需要用户确认的点：
    - “最近生产级别的主版本”是否允许 **跨主版本破坏性升级**（例如 `thiserror 1→2` 这类），还是只做同主版本的最新 minor/patch？
    - 是否有 MSRV（最低 rustc 版本）约束需要遵守？

## 2. 意图假设集（Hypotheses）

### H1

- 假设：你希望把 `Cargo.toml` 的直接依赖整体升级到“最新稳定主版本”（必要时改代码适配），并通过测试保证不回归。
- 关键分歧点：如果你只想做 `cargo update`（锁文件层面的升级）而不改 `Cargo.toml` 版本约束，则 H1 失效。
- 最小验证问题：本轮是否允许对少数关键依赖做跨主版本升级（例如 1.x → 2.x）？
- 当前证据：你的描述明确提到“到最近生产级别的主版本”“评估兼容性”“充分测试”。
- 反例/失败模式：一次性升级过多导致排障成本陡增、无法定位回归来源。
- 置信度：中

### H2

- 假设：你希望以“最小风险”为主，只升级到当前主版本内的最新 minor/patch（并尽量不改代码）。
- 关键分歧点：如果你明确要求“主版本必须跟到最新”，即使需要改代码，也要上，则 H2 失效。
- 最小验证问题：是否把“稳定/低风险”优先级放在“尽可能新”之前？
- 当前证据：你强调“生产级别”“充分测试”“不引入新问题”。
- 反例/失败模式：长期停留在旧主版本，错过关键 API 与安全修复。
- 置信度：中

## 4. 结论与边界（Conclusion）

- 最终意图（当前最可能）：以直接依赖为中心，分阶段升级到最新稳定版本（必要时跨主版本），并用编译+clippy+单测+最小运行验证兜底。
- 明确不做/不选项：不做无关重构；不在缺少证据时凭记忆改 API。
- 结论有效前提：升级过程中可运行测试与最小运行路径；若关键依赖最新版本存在已知不稳定/破坏性变更，将允许保守锁定并在报告中说明原因。
